## 目标与边界

- 能方便地新增、修改、发布技术笔记和生活记录。
- 能通过全文搜索、分类、标签和时间归档找到旧内容。
- 保留灰绿纸色、细线网格、终端对话与栞濑角色的辨识度。
- 文章正文优先保证阅读、代码和图片的展示质量。

第一版不包含登录后台、数据库、评论、点赞、访问统计、热门排行、订阅和真正可交互的角色 agent。避免动画阻挡文章入口，避免为了展示而增加写作负担。

2. 继续扩展单文件 HTML。初期修改少，但内容与渲染逻辑集中，文章增长后维护成本更高，因此不采用。

实施计划采用 Astro 静态生成、TypeScript、Markdown Content Collections、原生 CSS、Shiki、Pagefind 与 npm；GitHub Actions 构建后经 SSH 部署。服务器优先复用已有 Web 服务，无现有服务时考虑 Nginx；不引入无必要的服务端依赖。分阶段任务与验收见 `docs/superpowers/plans/2026-11-13-personal-blog.md`。

## 页面与信息结构

### 首页

顶部保留站点名称、导航和主题切换；主体保留角色坐在终端卡片上的构图。卡片提供清楚的文章入口，下方为最近记录和技术、生活两个分区入口。

终端对话作为短暂的装饰效果，不能阻挡点击；同一次浏览中不重复播放。具体文案在实现时作为可替换配置，不默认把参考内容当成作者真实表达。

### 文章列表与标签

以标题、摘要、日期和标签构成紧凑列表，避免强制要求封面。支持全部、技术、生活分类；点击标签可查看同标签文章。未填写摘要时从正文纯文本中生成简短摘要。

### 文章详情

正文宽度约 700–760px。展示标题、发布日期、可选更新日期、分类和标签。电脑端在空间足够时展示侧边目录，手机端使用可收起目录。

支持常见 Markdown、表格、任务列表、代码语法高亮、代码复制、图片和引用提示。长代码和宽表格在自身容器内横向滚动。页面提供回到列表和上一篇、下一篇入口。

### 搜索与归档

静态生成搜索索引，在浏览器中搜索已发布文章的标题、正文与标签，兼顾中文查询，显示可直接打开的结果和无结果状态。草稿不进入索引。

归档按发布日期倒序，按年份、月份组织；更新旧文章不改变它在归档中的原始时间位置。

### 关于与不存在的页面

关于页使用 Markdown，介绍内容由作者后续填写。不存在的文章地址展示清楚的返回入口。参考文章仅用于开发预览，不作为正式发布文章。

## 写作与内容约定

建议目录：`content/posts/<文章标识>/index.md`，图片与 Markdown 放在同一个目录，正文使用相对路径引用。实际目录可随框架调整，但保持文章与图片一起迁移的能力。

建议文章头部格式：

```yaml
---
title: 一篇笔记的标题
date: 2026-11-13
category: 技术
tags: [前端, 踩坑]
draft: true
# updated: 2026-11-15
# description: 可选摘要
---
```

- 标题和发布日期必填；分类仅为技术、生活；标签可为空。
- 新建模板默认草稿。草稿状态缺省时按草稿处理，作者显式设置 `draft: false` 后才发布。
- 本地预览可以查看草稿；生产构建排除草稿页面、链接和搜索内容。
- 文章目录名作为稳定标识，生成 `/posts/<文章标识>/` 独立地址；修改标题不改变链接。
- 日期按作者所在的 Asia/Shanghai 日历语义处理，避免纯日期因时区转换偏移一天。
- 缺少必填字段、重复标识或无效日期时给出包含文件路径的构建错误。

写作流程：复制模板 → 填写元信息与正文 → 放入图片 → 本地预览 → 将草稿设为已发布 → 构建并部署。提供简短的本地运行、写作与发布说明。

## 视觉、角色和适配

以参考页面的灰绿背景、深绿文字、轻边框、小圆角和留白为基础。细网格主要用于首页，正文保持干净。

`character-seated-breathing.webp` 作为首页角色素材，`icon.png` 作为站点图标，不默认将角色图标当作作者头像。优先复用参考资源，不重新生成角色。

保留明暗主题，记住选择，首次访问跟随系统。减少动态效果的系统偏好下，取消打字和闪烁，角色使用参考目录可用的静态素材；如无静态素材，则从已授权动画资源提取静帧。手机端缩小角色，保证导航、入口和正文可用。

## 发布边界与实施者可决定的事项

用户已确认部署到自己的云服务器。产物为静态文件，由服务器上的 Web 服务提供访问，博客本身无需常驻应用进程或数据库。

用户已确认使用公开的 GitHub 仓库管理版本，并集成 CI/CD 自动部署。代码、Markdown、图片、依赖锁文件和流水线配置一起纳入版本管理；构建产物不作为源码提交。

用户授权开发过程中在合适时机自行创建 Git 分支，以便后续开发。采用 main 作为稳定分支，按阶段或独立功能创建开发分支；阶段验收后合并，相关小修改可在当前分支完成，不要求每次建分支都再次确认。自动部署启用后，开发分支仅执行检查，main 的更新触发正式发布。

建议使用 GitHub Actions：本地写作与预览 → 提交并推送至 GitHub → 自动校验与生产构建 → 通过后部署到云服务器。默认方案为推送 `main` 自动部署，其他分支与 PR 只执行检查；支持手动触发发布。分支名属于实施建议，可根据实际仓库调整。

CI 检查包括依赖安装、项目类型检查（如适用）、文章元信息验证和生产构建。只有检查成功才进入部署阶段，部署使用同一次运行生成的构建产物，确保线上版本可追溯到提交。

在服务器支持 SSH 的前提下，建议通过专用部署账户上传到按提交标识划分的版本目录；上传完整后切换站点当前版本，避免读者访问到只上传了一部分的页面。生产部署串行执行，避免旧构建覆盖新版本；构建或上传失败保留原站点。保留上一版本，并提供手动回滚说明；切换后的访问检查失败时恢复上一版本。具体版本切换机制随服务器系统与 Web 服务确定。

部署凭据放在 GitHub Actions Secrets，服务地址和目录等非敏感配置使用变量；私钥不进入仓库。SSH 连接校验服务器主机密钥，部署账户仅拥有必要站点目录权限。具体 Web 服务优先复用服务器已有配置。

服务器系统、现有 Web 服务、站点目录、域名、HTTPS、SSH 可达性以及 GitHub 仓库地址尚未确认，在准备实际部署时根据环境确定。实施时提供本地可运行、可构建的成果及 CI/CD 配置；实际连接服务器、配置 GitHub 凭据、首次上线和调整服务配置不在当前设计阶段执行。部署配置需要保证文章独立地址可直接打开和刷新，并提供清楚的不存在页面。

仓库公开：提交到仓库的 Markdown 草稿与历史提交也属于公开内容。`draft` 仅控制是否发布到网站，不承担源码保密功能；私人记录与本地凭据不纳入版本管理。

实施者可决定组件拆分、静态框架、搜索实现、响应式断点、标签地址编码和细节间距，但应维持上述写作约定与视觉方向。新增依赖应保持必要且适量。

## 验收要点

- 新增一篇 Markdown 可形成文章详情、列表、分类、标签、归档和搜索结果。
- 草稿在生产输出中不可访问且不可搜索；本地预览可见。
- 图片相对引用可用，代码可复制，长内容不撑破手机布局。
- 中文搜索、无文章状态、无搜索结果和不存在的地址表现清楚。
- 首页延续参考构图，入口不依赖动画完成；明暗主题与减少动态效果设置生效。
- 首页、列表、归档、关于和正文在相同视口与主题下对照原始 HTML 验收，确认整体辨识度延续并说明优化点；不要求像素一致，不另换模板或大幅改变视觉方向。
- 生产构建通过，独立文章地址可直接打开和刷新。
- GitHub 检查失败时不部署；主分支成功构建后自动部署，部署版本可追溯到提交。
- 部署失败不留下半成品站点，并可恢复上一已发布版本。
